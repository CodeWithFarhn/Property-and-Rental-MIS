1.6 HTMX Global Patterns
These patterns are used consistently throughout the system. Developers should implement them once as base templates and reuse.
Modal pattern: hx-get fires on button click, loads a Django partial HTML form into a Bootstrap modal div (#modal-container). On form submit, hx-post sends data; success swaps the target table row or list. The modal closes via Alpine.js x-data toggle.
Live fetch pattern: hx-trigger='change' on a <select> fires hx-get to load related data into a #detail-panel div below the dropdown. Used on payment form (tenant select → loads balance), invoice form (lease select → loads period info).
Toast notifications: Every HTMX response includes an HX-Trigger header with a toast event. Alpine.js listens and shows a temporary success/error toast in the top-right corner. Auto-dismisses after 3 seconds.
Inline row update: After editing a table row, HTMX swaps only that row using hx-swap='outerHTML' hx-target='closest tr'. No full page reload.
Confirm delete: Alpine.js x-data shows an inline confirmation prompt on the same row before sending hx-delete. No browser confirm() dialog.
Loading indicator: Every HTMX button shows htmx-indicator class spinner during fetch. AdminLTE's overlay spinner used for full-panel fetches.
Global error handler: A single Alpine.js listener on document.body for htmx:responseError catches all HTMX 4xx/5xx failures. Fires a red toast: 'Something went wrong. Please try again.' with the HTTP status code. Implemented once in base.html — covers every page automatically. No per-page error handling needed.
1.7 Implementation Decisions (from Technical Audit)
The following decisions were finalised after reviewing an external technical audit. They are documented here so all three members implement consistently.
Decision
Rule
CNIC storage vs display
DB stores 13 raw digits in CHAR(13) — no dashes, no spaces. Django form clean_cnic() strips dashes before saving. A template filter cnic_display formats 13 digits as XXXXX-XXXXXXX-X for all UI display. The PDF receipt uses the formatted version. Never store dashes.
BEFORE UPDATE trigger
The existing INSERT trigger on leases_lease only fires on new rows. Add a matching BEFORE UPDATE trigger: if NEW.is_active = 1 AND OLD.is_active = 0, check that no other active lease exists for that unit. Prevents reactivating an old lease that would create two active leases.
System actor in audit log
actor_id is already nullable in the schema. Convention: NULL actor = automated system action (cron jobs, lease expiry checks, notification sends). The log_action() helper accepts actor=None. Dashboard displays NULL actor as System in italic gray text.
Property hard delete (by design)
RESTRICT on Property/Unit delete is intentional. A property with any lease history must never be hard-deleted. Instead: add a status field to properties_property (ACTIVE / ARCHIVED) in Phase 2. Archived properties are hidden from active lists but all historical data is preserved.
account_balance cache
The cached account_balance field is updated atomically on every payment save and invoice creation. It is used only for fast UI lookups. The B=(P×M)−ΣR formula computed in Django annotations is always the source of truth for reports and balance displays. If they ever diverge, the formula wins.
Service-awareness checks
Before any service-gated action (maintenance ticket creation, settlement generation, lease PDF), call contracts.services.property_has_service(property_id, service_slug). If False, return an HTMX partial showing a 'Service not included in this property contract' banner — never a 404 or silent failure. Slugs: tenant-management, maintenance, legal, financial-reporting, dedicated-manager.
Contract layer coupling
owner_id stays on properties_property — do not remove it. ContractProperty sits alongside as the commercial layer. Phase 1 data migration: on first Phase 2 migrate, a RunPython data migration auto-creates a default ACTIVE contract for every existing owner, enrolls all their properties, and assigns all services. This keeps the system operational immediately after migration with no manual setup.
Document storage
Individual FileField per model. Four document fields across existing models: OwnerContract.agreement_document (scanned signed agreement PDF, uploaded by staff), Payment.proof_document (bank slip or transfer screenshot, optional), MaintenanceTicket.cost_document (vendor invoice or repair receipt, optional when resolving), MonthlySettlement.remittance_proof (bank transfer confirmation, optional when marking remitted). Tenant documents handled by id_document field and Phase 3 vault. Accepted types: PDF, JPG, PNG. Max 10MB per file. Storage path: MEDIA_ROOT/documents/app/year/month/. Files always served via a Django view with @login_required and ownership check -- never via direct MEDIA_URL.

11. Tenant Self-Service Portal
The tenant portal lives at /tenant/ and uses a separate, simplified layout — no AdminLTE sidebar. Instead: a clean top navbar with the system logo, the tenant's name, and a logout link. The sidebar is replaced by a simple horizontal tab navigation. The design is intentionally lighter and more consumer-facing than the admin panel.
All views in this section are filtered to request.user only. A Tenant can never access another tenant's data — querysets enforce this at the Django level, not just the UI.
