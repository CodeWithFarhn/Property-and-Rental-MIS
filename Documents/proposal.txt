1. Project Overview
This document is the complete development plan for a Rental Property Management Information System (MIS) built as the CSC-458 group assignment. It covers the system scope, technology stack, database schema, user roles, feature set, and a three-phase build plan with explicit testing checkpoints between each phase.
1.1 Problem Statement
Property managers and landlords in Pakistan typically rely on manual methods — paper ledgers, spreadsheets, and WhatsApp — to track rent payments, tenant agreements, and property vacancies. This leads to:
Missed or unrecorded payments and no audit trail
Duplicate invoicing and manual reconciliation errors
No proactive alert system for overdue rent or expiring leases
Data loss risk with no centralised, backed-up system
No role separation — caretakers, owners, and managers all share the same information channel
1.2 Proposed Solution
A web-based MIS that centralises property management operations across four user roles, automates financial calculations, and eliminates manual reconciliation. The system will be accessible from any browser with no installation required.

4. Core Financial Formula
The outstanding balance calculation is the most important business logic in the system. It is defined as:
B  =  ( P  ×  M )  −  ΣR
Symbol
Variable
Definition
B
Outstanding Balance
The total amount the tenant owes as of today (PKR)
P
Monthly Rent Price
The agreed monthly rent from the active Lease record (PKR)
M
Months Since Move-In
Number of complete months elapsed since lease start_date
ΣR
Sum of All Payments
Total of all Payment.amount_paid records linked to this tenant's invoices
This formula is computed live in the tenant list view and the payment entry form using a Django annotated queryset. It is also the basis of the Rental Balances Report and the outstanding balance KPI card on the dashboard.
5. Three-Phase Development Plan
Each phase ends with a defined testing checkpoint. The next phase must not begin until the current phase passes its checkpoint. This ensures the system is always in a demonstrable state.
Phase 1  ·  Days 1–3
Core MVP — Working System
Goal: A fully functional system where a manager can register properties and units, onboard a tenant with a lease, generate an invoice, record a payment, and see the outstanding balance update correctly. Authentication and RBAC are fully implemented.
Phase 1 Features
F1.1 — Custom User Model & Authentication
Extend AbstractUser with role field (ADMIN, MANAGER, STAFF, OWNER, TENANT)
Login page with session-based auth and bcrypt password hashing (Django default)
Session timeout middleware — auto-logout after 30 minutes of inactivity
Role middleware — redirects each role to its correct dashboard on login
All views protected by @login_required and a custom @role_required decorator
F1.2 — Location & Property Management
Location model: predefined list of Karachi areas as admin-managed dropdown values
Property CRUD: name, address, location, owner assignment
Unit CRUD: unit_number, type, bedrooms, monthly_rent, status (VACANT/OCCUPIED/MAINTENANCE)
Unit availability filter: only VACANT units shown in tenant assignment dropdown
Unit status auto-updates: OCCUPIED on lease creation, VACANT on lease termination
F1.3 — Tenant Registration (with Atomic Transaction)
Tenant form: full_name, email, phone, CNIC, profession, emergency contact, ID document upload
Unit assignment dropdown (VACANT only)
Lease creation form: start_date, end_date (optional), monthly_rent, deposit details
All three operations (Tenant insert, Lease insert, Unit status update) wrapped in a single Django atomic transaction block — full rollback on any failure
Soft-delete: tenant exit sets status=INACTIVE, lease is_active=False, unit reverts to VACANT (atomic)
F1.4 — Invoice Generation
Generate monthly invoice per active lease
Duplicate prevention: unique constraint on (lease, period_month) — one invoice per month per tenant
Auto-apply account credit: if tenant.account_balance > 0, deduct from amount_due before saving
If credit fully covers the invoice, set status=PAID immediately
Invoice number auto-generated: INV-YYYYMMDD-HHMMSS
F1.5 — Payment Recording
Payment form with tenant dropdown (shows tenants with UNPAID/PARTIAL invoices only)
HTMX live fetch: selecting a tenant loads their current balance, monthly rate, and invoice details without page reload
Supports partial payments — multiple payments against one invoice, balance recalculated each time
Payment methods: Cash, Bank Transfer, EasyPaisa, JazzCash, Cheque
reference_code field for transaction ID or receipt number
On payment save: update invoice.amount_due, update invoice.status, update tenant.account_balance — all atomic
F1.6 — Outstanding Balance Auto-Calculation
Balance computed using B = (P x M) - SR formula in Django queryset annotation
Displayed live in tenant list, payment form, and tenant detail view
Correctly handles partial payments, overpayments, and month boundaries
F1.7 — Role-Specific Dashboards
Admin/Manager dashboard: total units, occupied units, vacant units, total rent collected this month, overdue balances, recent activity
Owner dashboard: same KPIs filtered to their own properties only
Staff dashboard: simplified view — just today's payments and open maintenance tickets
All KPI cards are dynamic — computed from DB, not hardcoded

Phase 2  ·  Days 4–5
Automation Layer — Professional System
Goal: Add the features that separate a basic tracker from a professional system — PDF generation, notifications, audit trail, maintenance ticketing, and financial reporting. Phase 1 must fully pass its checkpoint before starting Phase 2.
Phase 2 Features
F2.1 — PDF Receipt & Invoice Generation
WeasyPrint installed. Django view renders a dedicated HTML template and returns it as a PDF download response
Payment receipt PDF: tenant name, unit, lease period, amount paid, payment method, reference code, date, system branding
Monthly invoice PDF: invoice number, period, amount due, due date, tenant details
Download button on payment confirmation page and invoice list
F2.2 — Email Notifications
Django email backend configured. In development: EMAIL_BACKEND = 'django.core.mail.backends.console.EmailBackend' (printed to terminal, no SMTP needed)
For demo: switch to Gmail SMTP with an app password
Trigger 1 — Invoice created: email tenant with invoice details and due date
Trigger 2 — Payment recorded: email tenant with receipt summary and remaining balance
Trigger 3 — Lease expiry warning: daily management command checks for leases expiring within 30 days and emails manager
All emails also saved to Notification model with channel=EMAIL, status=SENT
F2.3 — SMS Notifications (Simulated)
SMS function takes (phone_number, message) and saves to Notification model with channel=SMS, status=SIMULATED
No external API called — zero cost
Trigger events: tenant admission welcome, invoice creation, payment confirmation
SMS log viewable in admin panel — shows exactly what would have been sent
F2.4 — Audit Trail
AuditLog model created. Helper function log_action(actor, action_code, description) called after every significant operation
Logged events: tenant admitted, lease created, invoice generated, payment recorded, user created, unit status changed, maintenance ticket updated
Dashboard: last 10 audit entries shown in a live-updating panel
Unseen entries (seen=False) shown as notification badge count in navbar
HTMX: clicking 'mark as seen' updates seen=True without page reload
F2.5 — Maintenance Request System
Tenant portal: submit ticket form with title, description, urgency level, optional photo upload
Manager view: list of all open tickets, assignee dropdown (Staff users only), status update
Staff view: tickets assigned to them — can update status to IN_PROGRESS or RESOLVED
Cost field unlocked when status = RESOLVED — manager logs repair cost
Unit set to MAINTENANCE status when a CRITICAL ticket is opened. Cleared on ticket CLOSED.
F2.6 — Financial Reports
Monthly Payments Report: filter by month, shows all payments with tenant, unit, invoice ref, amount. Total at footer. Print button opens print-formatted view.
Outstanding Balances Report: all active tenants with monthly rate, months payable, total paid, outstanding balance, last payment date
Both reports exportable via DataTables Buttons (CSV, Excel, PDF, Print)
Owner-filtered versions: same reports but scoped to Owner's properties only
F2.7 — System Settings
Single-record settings model: organisation name, contact email, phone, currency symbol, late fee percentage, grace period days
Logo upload — displayed in PDF headers and dashboard
Settings loaded into request context via context processor — available in all templates

Phase 3  ·  Days 6–7
Polish & Tenant Portal
Goal: Add the tenant self-service portal, document vault, and occupancy chart. Final polish pass on UI. Reserve time for IEEE report writing — do not spend more than one day on Phase 3 features if report is not drafted.
Phase 3 Features
F3.1 — Tenant Self-Service Portal
Separate login flow for Tenant-role users. Redirects to /tenant/dashboard/ not /admin/.
Tenant dashboard: current balance, active lease details (unit, rent, start/end date), last payment date
Payment history: chronological list of all payments with downloadable PDF receipt per payment
Maintenance requests: view submitted tickets and their current status
Tenant cannot see other tenants' data — all querysets filtered by request.user
F3.2 — Document Vault
Upload and manage documents per tenant: CNIC, rental agreement, NOC, reference letters
Each document has: document_type, file, upload_date, expiry_date (optional)
Dashboard warning card: documents expiring within 30 days flagged in amber
Manager can download any document from the tenant detail page
F3.3 — Occupancy Trend Chart
Line or bar chart on Admin/Manager dashboard showing monthly occupancy rate over the past 6 months
Rendered using Chart.js (CDN, free). Data computed server-side and passed as JSON to template.
Owner dashboard shows the same chart filtered to their properties
F3.4 — UI Polish
AdminLTE theme fully applied across all pages — consistent sidebar, navbar, breadcrumbs
All HTMX interactions have loading indicators (spinner during fetch)
All forms have client-side validation (HTML5 + Alpine.js) before server submission
Mobile responsiveness verified on phone screen width
Empty state messages for all list pages (e.g. 'No tenants yet — add your first tenant')
